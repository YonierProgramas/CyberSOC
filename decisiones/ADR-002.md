# ADR-002 — SQLite bajo responsabilidad exclusiva del Core

## Contexto

La aplicación necesita conservar configuración, trabajos, resultados y, progresivamente, evidencias, decisiones, análisis de IA y auditoría. La persistencia debe sobrevivir a reinicios y mantener resultados ya guardados ante cancelaciones o fallos. La arquitectura asigna el estado de la aplicación al Core TypeScript y prohíbe el acceso a SQLite desde el motor Python.

Fuentes: D3 de [00-ESTADO.md](../00-ESTADO.md), [resumen general](../01-resumen-general.md), «Migración 001» y «Spike de SQLite» del [plan S0](../sprints/sprint-00-foundation/plan.md).

## Decisión

Se propone utilizar SQLite local, con acceso exclusivo desde el Core ejecutado en main. El renderer solicitará operaciones mediante IPC; Python devolverá resultados por RPC sin acceder a la base. Los repositorios encapsularán las consultas y `MigrationRunner` aplicará las migraciones pendientes.

Main inyectará en `Database` la ruta `app.getPath('userData')/cybersoc.db`. Las pruebas utilizarán una ubicación temporal. Al abrir la conexión se activarán `PRAGMA journal_mode=WAL` y `PRAGMA foreign_keys=ON`.

La migración inicial creará `schema_migrations`, con versión, nombre y fecha de aplicación, y `settings`, con clave, valor JSON y fecha de actualización. Reiniciar la aplicación no deberá reaplicar una migración registrada. Las modificaciones de migraciones ya aplicadas requerirán un ADR aprobado.

La biblioteca se seleccionará mediante el spike previsto en S0, con duración máxima de dos horas. Este ADR conserva el criterio de selección sin atribuir resultados no documentados al experimento.

## Alternativas consideradas

| Alternativa documentada | Criterio de selección |
|---|---|
| `node:sqlite` | Primera opción del spike; debe funcionar con la versión de Electron del proyecto en desarrollo, Vitest y CI |
| `better-sqlite3` con `@electron/rebuild` | Alternativa si falla la primera; las pruebas se ejecutarán sobre el runtime de Electron y no deberán exigir compilación nativa manual |

Ambas opciones conservan SQLite bajo responsabilidad del Core. No se documenta una evaluación de otros sistemas de base de datos ni se propone distribuir su acceso entre procesos.

## Consecuencias

- La escritura y las migraciones tienen un responsable único, coherente con el control de estados y transacciones del Core.
- Renderer y motor dependen de las operaciones de aplicación para consultar o conservar información; no manejan conexiones propias.
- Deben probarse una base nueva, la ejecución repetida de migraciones y la persistencia tras reiniciar.
- La compatibilidad de la biblioteca con Electron, el entorno de pruebas y CI requiere evidencia del spike; no puede darse por demostrada mediante este documento.

## Estado

**PROPUESTA.** D3 permanece propuesta en `00-ESTADO.md`. Las fuentes de planificación consultadas no incluyen un resultado del spike que permita cerrar aquí la elección de biblioteca. Quedan pendientes su evidencia y aprobación; no se cambia el esquema ni se ejecutan migraciones con esta redacción.
